Text Skill Documentation
./docs/examples/text24.asm — 24-Character Text Display
Core Technique: Uses player/missile sprites (GRP0/GRP1) to render text characters. Each character is 5 bytes tall × 8 pixels wide, rendered via the TEXTDISP macro pattern.
Key Structures:
- ZP variables: Text0-Text23 store character indices; left_text/right_text arrays define 5-byte pixel patterns per character
- Horizontal positioning: SetHorizPos subroutine computes HMP0/RESP0 using coarse/fine division (subtract 15, eor #7, table lookup) — positions sprite LEFT edge at requested pixel 0-159
- Frame alternation: Two frame states (____frame0_text and StartFrame1Text) alternate which text buffer is rendered each frame
- 5-line text rendering: Five TEXTDISP blocks render 5 text lines, each line using 2 characters (left+right) from the font set
- Timing: VBlank uses TIM64T=44 (~37 scanlines); overscan uses TIM64T=36; each scanline must complete within 76 CPU cycles
Character Font (text_data section): 5-byte patterns for A-Z, space, period, question mark, exclamation, comma, hyphen, plus — stored as left/right halves that are ORed during rendering
Critical Pattern: The TEXTDISP macro sequence (lines 127-154 in text24.asm) shows the exact cycle-critical pattern: sta WSYNC → sty COLUP0/1 → sta GRP0 → load left char → ora right char → sleep 2 → sta GRP1 → etc. The sleep N macros insert NOPs to pad exact cycle counts.
./docs/tutorial/13_plus2.asm — 13+2 Character Demo
Core Technique: Similar sprite-based text rendering but with a different variable organization and font table layout. "13_plus2" refers to 13 printable characters plus 2 additional decorative chars.
Key Structures:
- RAM variables: charp=$80, chara=$85, charb=$8a, charc=$8f, chard=$94, chare=$99, charf=$9e, charg=$a3 — these are ZP pointers for the 8 characters rendered per "line group"
- TEXTDISP macro (lines 59-87): Sets NUSIZ1=$03 (3 sprite copies), VDELP1, ENAM0/1/ENABL, then writes GRP0/GRP1 with 5-byte font data. The macro renders exactly 2 characters per scanline cycle.
- Font tables: fonthi (high bytes of font addresses) and fontlo (low bytes) — indexed by character code. Font data is 5 bytes tall, stored as %xxxx xxxx bits (8 pixels wide per byte).
- mainTextLoop: Loads text characters from text/text1 arrays (null-terminated at byte 0), builds display list via PHA pushes, then renders via 5 TEXTDISP 0,0 through TEXTDISP 4,8 calls
- Variable mapping: textptr and text1 arrays control which characters are rendered; chars equ $a7 (=167) marks end-of-text terminator
Game Loop: Standard VSync→VBlank→Picture→Overscan loop. Picture render sets PF0=$F0, PF1=$F0, PF2=$00 with CTRLPF=$05 (reflected playfield). Playfield color COLUPF=$28 (orange/brown).
Critical Timing Insight: The demo preserves the exact cycle phase from the original 13_plus2 tutorial — TEXTDISP must be preceded by HudCopy and WSYNC for correct horizontal positioning. Omitting the leading sta WSYNC or the fixed NUSIZ1=$03 setup displaces the glyphs.
32-Character Text Solution (AtariAge Forums — Eshu's Routine)
Source: AtariAge forum thread "Text kernel" (topic #295680), Reply 34 by eshu.
Technique: Renders 32 characters total on a stock 4K ROM. Each row of text is rendered into ZP RAM over a number of scanlines before it gets displayed.
Key Insights:
- Not perfect: Off-center positioning and minor character spacing artifacts are "insurmountable" but "acceptable"
- Verified: Works in both Stella emulator and on Harmony cartridge hardware
- Stock 4K ROM: Uses no bankswitching tricks — fits within standard 4K cartridge window
- Pre-rendering approach: Each text row is rasterized into ZP RAM during blanking intervals, then displayed — avoids real-time computation during kernel
- Preferred over 36-char demo: Forum consensus: "if you want simple re-usable on stock hardware then I would stick with Eshu's 32 character routine" (vs. Thomas Jentzsch's 36-char demo which may require more specialized hardware)
Tradeoff: 32 characters is the practical limit for a re-usable, stock-hardware-compatible routine. Going to 36 characters pushes the cycle budget too far.

font_manager System Design
Based on the analysis of all three sources and the constraints specified, here's the designed system:
Design Constraints (as specified)
- Generic enough for start screen and game use without timing breaks
- Positionable anywhere on screen without breaking
- Min 8 chars/line (otherwise very difficult to write anything)
- Min 2 lines
- Limited colors
- Can have low refresh rate (30 fps) and flicker if helpful
System Architecture
1. Font Format (5 bytes per character, 8 pixels wide)
- Each character = 5 bytes, one byte per row (5 rows tall)
- Each byte bits 7-0 represent 8 horizontal pixels (1=on, 0=off)
- Compact: 40 bytes per line of 8 characters, 200 bytes for 50 characters
- Compatible with both text24.asm and 13_plus2.asm font approaches
2. Text Storage (Zero Page RAM)
ZP $B0-$BF: Font table pointer (2 bytes)
ZP $C0-$DF: Text buffer (up to 28 chars × 5 rows = 140 bytes, or line-based)
ZP $E0-$EF: Rendering temporaries
- Lines are null-terminated (byte 0 = null end marker)
- Maximum 32 chars per line (practical: 8-12 for readability)
- Two text buffers for flicker alternation (30 fps)
3. Rendering Approach (hybrid of sprite-based and pre-rendered)
- During VBlank: Pre-render next frame's text into ZP display list
- Convert text characters to GRP0/GRP1 sprite values
- Pre-calculate HMP0/HMP1 fine offsets for each character
- Pre-calculate VDELP0/1 vertical positions
- During Kernel: Read pre-rendered display list, write GRP0/GRP1 per scanline
- Use WSYNC-absorbed loop similar to TEXTDISP pattern
- Write GRP0/GRP1 at exact scanlines for each character row
- 5 rows per character rendered across 5 scanlines
4. Positioning Mechanism
- Horizontal: SetHorizPos routine (same as text24.asm) - uses HMP0/X fine offset table
- X coordinate 0-159 → HMP0 fine nibble from lookup table
- Table maps remainder (-15 to -1) to exact HMP nibble
- Page-aligned table provides critical extra cycle for precision
- Vertical: Player Y position ($81 ZP) determines scanline
- VDELP0/1 add vertical delay (1-7 scanlines)
- Can position at any scanline 0-191
- Cross-bank safe: Fold pads at $FC68/$FC70 ensure code continues after bank switch
5. Color System
- COLUP0 controls GRP0 color (player 0 / text color 1)
- COLUP1 controls GRP1 color (player 1 / text color 2)
- Can cycle colors per line or per frame for variety
- Background: COLUBK ($06 grey default, or any color)
- Playfield: COLUPF ($28 orange default from 13_plus2)
6. Flicker / 30 fps Support
- Double-buffer text: Two text buffers (text_buf and text_buf2)
- Odd frames render from buffer A, even frames from buffer B
- Or: Hold each frame for 2 VBLANKs to achieve ~30 fps
- Flicker is acceptable per constraints and helps with timing
7. Line Minimum (2 lines)
- Always render at least 2 lines of text
- Lines stacked vertically with Y offset
- Each line independent - can show different text
- Lines rendered in overscan area (scanlines 144-191) or within kernel
8. Character Limit (min 8 per line)
- Each line supports 8-32 characters
- 8 chars × 8 pixels = 64 pixels wide (leaves 96 pixels of the 160-wide screen)
- Can center text or left-align
- Fewer than 8 chars makes font too sparse to be readable
Timing Workflow
Frame Start (VBlank ~37 scanlines):
  1. Read joystick input
  2. Update text buffer (or switch buffers for flicker)
  3. Pre-render display list: convert text chars → GRP0/GRP1 values
  4. Calculate HMP0/HMP1 fine offsets for each character position
  5. Set VDELP0/1 for vertical positioning
  6. Set WSYNC, HMOVE

Kernel (192 scanlines):
  7. Per scanline: WSYNC, then write GRP0/GRP1 from display list
  8. Advance display list pointer per character row
  9. If end of text, write blank GRP0/GRP1

Overscan (30 scanlines):
 10. Reset sprite positions for next frame
 11. TIM64T wait, then jump to VBlank

font_manager	Pre-rendered display list

High-Level System Explanation
The font_manager system works by decoupling text rendering from real-time scanline constraints through pre-computation during VBlank, while maintaining the flexibility to position text anywhere on the Atari 2600 screen.
Core Design Philosophy
The Atari 2600 has extremely tight timing (76 cycles per scanline, 262 scanlines per frame). Real-time text rendering (as in text24.asm and 13_plus2.asm) requires exactly cycle-perfect code that's fragile and difficult to position generically. The font_manager instead:
1. Pre-renders during VBlank: The 37+ scanlines of VBlank are used to convert text characters into pre-calculated sprite values (GRP0/GRP1 bytes, HMP fine offsets, VDEL settings). This happens once per frame, not once per scanline.
2. Uses player/missile sprites: Text is drawn using the two player sprites (GRP0/GRP1), which can be positioned anywhere on screen via HMP0/1 fine offsets and VDEL0/1 delays. This avoids the playfield rendering entirely, eliminating playfield-timing conflicts.
3. Double-buffered text buffers: Two text buffers allow flicker at 30 fps (or simpler single-buffer with frame alternation). The kernel simply reads from whichever buffer is "active."
4. Minimal constraints:
- 8 chars/min line: 8 characters × 8 pixels = 64 pixels, readable while leaving 96 pixels of the 160-wide screen for background/cave
- 2 lines minimum: Ensures text is always visible; lines can be stacked in the overscan area (scanlines 144-191) or within the kernel
- Limited colors: COLUP0/COLUP1 provide 2 text colors; COLUBK/COLUPF provide background
5. Cross-bank safety: The fold pads at $FC68 (bank0→menu) and $FC70 (bank1→game) ensure the text rendering code works in both banks without modification. The HudSlotsRam=$b3 ZP mirror and HudPtrLo/Hi=$db/$dc are shared across banks.
Usage Pattern
Start Screen (bank1):
- Initialize font table with desired characters
- Set up text strings (e.g., "AI SAVIOR" or game title)
- Pre-render during VBlank
- Kernel renders text using display list
- Player/sprite interaction happens around the text
In-Game (bank0):
- Same font table, different text strings
- Position text at any screen location (HUD corner, center, etc.)
- Dynamic text updates between levels
- Flicker enabled or disabled based on game state
The system is generic because: the font table can be any 5-byte-per-character set, text strings are data (not code), positioning uses variable ZP values (not hardcoded), and the VBlank pre-render step adapts to any text content without timing breaks.
