# Level Data in a Separate Bank — Investigation

**Status: IN PROGRESS — findings so far written; recommendation draft below
(may change if user finds the original plan)**
Date: 2026-09-27

## Problem statement

- Levels will grow in number and size; even optimized, level data will eventually
  occupy a full 4K bank.
- Game code lives in bank0 (kernel.asm). Level data currently lives in bank0 too
  (`generated/*.asm`, read directly by ROM routines) and bank0 is **full
  (4B free)**.
- Constraint: a 2600 ROM bank holds code AND data in one 4K image; data in bank X
  is only readable while bank X is selected. Switching away from bank0 also
  switches away from the code executing.
- Question: how to read level data from a data-only bank WITHOUT duplicating the
  game code into that bank? (Possible: a jump / mini-code trampoline.)
- Prior investigation (user + AI, session not preserved) concluded current 16K
  mapper fits our needs. Recreation target: mechanism design.

## Context / hard facts (verified this session)

- Mapper: **F6** (16K = 4 × 4K), hotspots `STA $1FF6`(bank0) `$1FF7`(bank1)
  `$1FF8`(bank2) `$1FF9`(bank3). All banks map at `$F000-$FFFF`.
- Banks today: bank0 = whole game (ends `$FC64`, 4B free before fold at
  `$FC68`); bank1 = HUD (`MenuMain` `$F540-$F9C3`, ~1300B fragmented free);
  bank2 = 5-byte stub (~4080B free); bank3 = power-up stub + reset vector
  (must keep).
- Power-up: bank3 selected at reset → its `$FFFC` → stub → bank0 `GameStart`.
- Existing cross-bank mechanism: **fold pads** `$FC68`/`$FC70` (identical bytes
  in bank0 + bank1), build guard in `verify_build.py`. Proven: guard caught a
  Overscan address drift this session.
- 2600 RAM = 128B total, fully allocated (`docs/zp_layout_skill.md`); stack
  owns `$F8-$FF`. No free ZP for shadow buffers today.
- Level data size now: 2 levels + models ≈ 150B in bank0. Per-level ≈ 60-80B.

## Investigation log

### 1. How is level data consumed today? (done)

Data layout (all generated by `convert_level.py`, included at
`kernel.asm:2277-2289`, ~8.3KB source ≈ ~1.2KB binary):

| Block | Contents | Shared? |
|-------|----------|---------|
| `models_data.asm` | Per model: `MxRoomRects` (count + x,y,w,h ×N + hot count) + `MxTilePF0/1/2` (12 rows × 3 = 36B) | shared across levels |
| `level_00N_rooms_data.asm` | per-room 4-byte records → model PF ptr + rects ptr? (53B) | per level |
| `levels_data.asm` | `LevelDataTable` stride 14: start(3) + miner(3) + wall_colors(2) + pfdata/conn/enemy ptrs(6) | per level |
| `level_00N_rooms.asm` | per-room enemy records (6B each, ≤3) + connection table (4B/room, $FF=none) + bottom_color | per level |

**All consumers already go through zero-page pointers** (this is the key fact
for every option):

| Pointer | Set by | Read by | Frequency |
|---------|--------|---------|-----------|
| `RoomPF0/1/2Lo/Hi` (→ `MxTilePF0/1/2`) | `EnterRoom` | `LoadPFBuffer` — 12 rows × 3 = **36 indirect ROM reads EVERY frame** (VBLANK; buffers get corrupted by bank1 HUD, must reload) | per frame |
| `RoomRectsLo/Hi` (→ `MxRoomRects`) | `EnterRoom` | `BombMarkWalls` (L2104), PHM walk (L2169/2437/2715), CEH (L2940) | per call, several/frame |
| `EnemyDataLo/Hi` (+count) | `EnterRoom` | `UpdateEnemies`, `DeriveEnemyY`, dispatch, `SelectActiveObject`, kill/reload — 16+ `(EnemyDataLo),Y` sites | per frame |
| `LevelPFDataLo/Hi` (→ rooms_data) | `LoadLevel` | `EnterRoom` (room→ptr table) | room entry |
| `LevelConnLo/Hi` (→ connections) | `LoadLevel` | `ExitRoomUp/Down/Left/Right` | room exit |
| `LevelEnemyLo/Hi` (→ room records) | `LoadLevel` | `EnterRoom` (ptr/count/color) + `LoadRoomBottomColor` (every frame! L640 kernel .WaterRow calls it) | per frame (1 read) |
| `LevelDataTable` (stride 14) | — | `LoadLevel` computes base+L*14, reads start/miner/colors | level load |
| miner spawn (`StartFrame`?) | `LoadLevel` | once | level load |

**Indirect loads are 6502 `(zp),Y` — the pointer value is just an address.**
Nothing in the consumers cares whether the data sits in bank0 ROM, another
bank's ROM, or RAM — only that the right bytes are readable at that address
**while the read executes**.

Sizes (binary): per room ≈ PF 36B + rects (~12-25B) + enemies ≤18B +
conn 4B + record 4B ≈ **~75-90B/room**; models shared (~5 models ≈ 250B now).
A dedicated 4K data bank ≈ **~45-50 rooms** at today's format.

### 2. RAM reality check (done)

- Total 2600 RAM = 128B; ZP fully allocated (`docs/zp_layout_skill.md`);
  `$F8-$FF` = stack. **No free buffer space for a full shadow copy** of
  PF rows (36B) + rects (20B) + enemies (18B) ≈ 74B.
- However: `PF0Buf/PF1Buf/PF2Buf` (36B) **already exist** — they hold exactly
  the PF row data, but must be re-copied from ROM every frame because the
  bank1 HUD corrupts them (`kernel.asm:1024` comment). Shadow-to-RAM would
  still need a pristine source to re-copy from each frame → doesn't remove
  the per-frame source problem.

### 3. How HERO does it (the reference architecture — decisive)

Disassembly evidence (`docs/hero/hero_bank0.asm` + `hero_bank1.asm`):

- HERO is **F8** (8K, 2×4K), hotspots `$1FF8/$1FF9` accessed via mirrored
  `BIT/STA $FFF8/$FFF9`.
- **HERO's per-frame PF/score lookup tables (`LFA00/LFB00/LFC00/LFD00`) live
  in bank1, and the code that reads them (`L384-L398`) is in bank1 too.**
  `grep LFA00 hero_bank0.asm` = **zero hits** — bank0 NEVER reads bank1 data
  directly.
- Cross-bank control flow = the fold trick: bank0 `START` at `$D000` runs
  `BIT $FFF9` (switch mid-stream) then `JSR $F000` — the following bytes are
  fetched from the *other* bank's file at the same offset. Our `$FC68/$FC70`
  pads are our implementation of the same idea.

**HERO's rule: the reader code always sits in the same bank as its data.**
Data never crosses a bank boundary — code does, via tiny identical-byte fold
regions. (This directly answers the user's question: yes — a mini-code that
jumps to the data's bank, reads there, and jumps back; HERO does exactly that,
and it does NOT copy game code into data banks.)

### 4. Mapper facts (E6/F6 clarification)

There is **no "E6"** in the standard bankswitch catalog. Candidates the prior
investigation likely compared (Kevin Horton sizes.txt + Stella autodetect):

| Type | Size | Banks | Extra RAM | Fit |
|------|------|-------|-----------|-----|
| **F6** (current) | 16K | 4×4K, `$1FF6-$1FF9` | none | ✅ chosen; build/editor already F6 |
| F6SC | 16K | same | **128B @ $1000** (Sara chip) | would make M1 shadow-copy free — but needs Superchip hardware, Stella emulates it |
| E0 | 8K | 3×2K | none | too small |
| E7 | 16K | 8×2K selectable + last 2K fixed | **2K @ $1000/$1800** | max RAM, but 2K-bank structure = rework everything |
| F4 | 32K | 8×4K | none | future growth if 16K ever really runs out |

Conclusion: stay **F6**. The fold mechanism (§4) is mapper-agnostic — it uses
only the bank-select hotspot, so it works identically on F6/F6SC/F4.

### 5. Where the per-frame reads actually are (cycle reality)

Inventory of ROM reads that happen **every frame** (the dangerous ones) vs
**cold** (room/level load — cheap to route through a fold):

| Read | Sites | When | Bank need |
|------|-------|------|-----------|
| `LoadPFBuffer` 36 × `(RoomPFxLo),Y` | 1 loop, VBLANK | every frame | reads `MxTilePFx` = **models** (shared!) |
| rect walks `(RoomRectsLo),Y` | BombMarkWalls, PHM ×3, CEH | several/frame, overscan | reads `MxRoomRects` = **models** (shared!) |
| enemy records `(EnemyDataLo),Y` | 16 sites (dispatch, derive, kill, reload) | every frame, overscan | **per-level** ✗ must cross banks |
| `LoadRoomBottomColor` `(LevelEnemyLo),Y` | kernel `.WaterRow` call! | **every frame, inside cave kernel** | **per-level** ✗ kernel-time read |
| `EnterRoom` table reads (`LevelPFData/LevelEnemy`) | 12 reads | room entry | cold ✓ |
| `ExitRoom*` `(LevelConnLo),Y` | 4 | room exit | cold ✓ |
| `LoadLevel` `LevelDataTable` stride-14 | ~14 | level load | cold ✓ |
| `GetConnIdx`/mine spawn/etc. | few | level load | cold ✓ |

**Critical structural insight:** models (PF rows + rects — ~90% of the bytes
and nearly all per-frame reads) are **shared across levels** and could stay in
bank0 → `LoadPFBuffer` and the rect walks need **NO fold at all**. What must
move to the data bank is only the **per-level** part: enemy records,
connections, rooms_data pointers, LevelDataTable, band colors — and of those
only two are per-frame (enemy records: overscan, foldable; band color: kernel,
must be **cached to ZP at EnterRoom** — a bank switch inside the cave kernel
is impossible because the kernel code itself lives in bank0).

That reduces the mechanism to: **a fold fetch used by (a) EnterRoom/LoadLevel/
ExitRoom cold reads, (b) ~10 enemy-record reads per frame in overscan, plus a
1-byte ZP cache for band color.** VBLANK/overscan budgets (2812c / 2240c)
have ample room for ~10 folds × ≈30c; a fold inside the 76c kernel scanline
budget does not — which is why band color caches instead.

### 6. Fold block design (concrete bytes)

Bank0 + each data bank contain **one identical byte region** at a fixed
address (mirror of `$FC68` idea):

```
; ---- 14B, identical in bank0 and data bank at $XXXX ----
FoldIndirect:                  ; bank0 caller: jsr FoldIndirect  (Y = index)
    lda #DATA_BANK_SEL         ; 2B — executed in bank0
    sta $1FF8                  ; 3B — switch to data bank, PC+5 continues below
    lda (FetchPtr),Y           ; 2B — executed in DATA bank (its copy)
    sta FetchTmp               ; 3B — preserve result across switch-back  (zp)
    lda #0                     ; 2B — select bank0
    sta $1FF6                  ; 3B — back to bank0; next byte fetched from bank0
    lda FetchTmp               ; 3B — executed in bank0
    rts                        ; 1B — returns to caller's jsr
; total = 19B (variants below shave this)
```

Variants: if the result can be staged in X/TMP differently, or `FetchTmp`
overlaps an acceptable scratch, the block shrinks toward 13-14B.
`FetchPtr` = one shared ZP pointer pair; routines copy their pointer into it
once per routine (8B of setup code each), then every `(ptr),Y` site becomes
`jsr FoldIndirect` (3B, returns A).

**Bootstrap problem (must solve first):** the fold block needs its
contiguous bytes in bank0 — and bank0 has **no 14B hole**:
- pre-fold: 4B (`$FC64-$FC67`)
- pre-vectors: 6B (`$FFF4-$FFF9`)
- real zero holes in post-pad: 9B `$FEF7-$FEFF`, 8B `$FEAF-$FEB6`,
  8B `$FF9E-$FFA5` (rest are data-fill, not free)
- (`$FB72-$FB7D` 12B is generated level-data padding — may vanish anyway
  when level data moves)

Options to raise 14B: (a) merge/relocate one post-pad leaf to widen the
`$FEF7` hole; (b) free bytes in main by dropping dead data (the `$FB72`
zeros); (c) shrink `LaserInput`/`SetObjReflection` tail by 5B. Any of these
is a small, testable first step — and the first real fold user can be a
trivial read (`LoadLevel` stride table), gated in Stella before the rest.

### 7. Mechanism candidates (detail)

- **M1 — shadow-copy to RAM at EnterRoom** (one-time copy, pointers → RAM):
  no per-frame bank switching, consumers unchanged. Blocked by RAM (74B
  needed, ~0 free) unless buffers are restructured (e.g. stop HUD
  corruption → PF buffers persist → only rects+enemies ≈ 38B needed).
- **M2 — fold fetch trampoline (user's "mini-code jump")**: tiny block of
  identical bytes at ONE fixed address in bank0 + every data bank:
  bank0 `jsr FoldBlock` → fold bytes `lda DataBankSel / sta $1FF6` →
  *(now executing data bank's copy of the block)* `jsr FetchBody` →
  `lda #0 / sta $1FF6` → *(back in bank0, same address)* `rts`.
  `FetchBody` lives only in data banks (~6-10B), never executed from bank0.
  Bytes duplicated: ~9-12B per data bank. **Zero RAM.** Cost ≈ 25-30c per
  data read + 3B + 6c per call site in bank0.
- **M3 — fold whole leaf routines**: instead of per-byte fetches, the
  routines that touch data (`LoadPFBuffer`, rect walker, enemy record
  readers) are themselves placed in the fold region / data banks and run
  there for their duration (switch → run → switch back → rts). Duplication
  ≈ 40-150B per data bank, but call sites become 1 switch each; per-frame
  overhead drops (one switch per call instead of per read).
- **M4 — keep game code out, duplicate data-adjacent loader only**: data
  bank = level data + a `LoadRoomShadow` routine; bank0 enters it via fold,
  copies per-room rects/enemies into RAM (if/when RAM freed) — M1+M2 hybrid.
- **M5 — mirror code into every data bank** (the naive "game code + data in
  same bank"): wastes ~2.5-3.9K per data bank; rejected (user's question
  explicitly rejects it; also halves bank slots).

### 8. Recommendation (draft for user review)

**Adopt HERO's rule + M2/M3 hybrid:**

1. **Split by growth, not by kind:** shared models (PF rows + rects, ~90% of
   bytes, all hot VBLANK/overscan reads) **stay in bank0** — `LoadPFBuffer`
   and rect walks keep their current direct reads, zero mechanism.
   Per-level growing data (enemies, connections, rooms ptrs, LevelDataTable,
   band colors) **moves to bank2** — that is the part that will fill a bank.
2. **Mechanism = fold fetch (M2)** for per-frame enemy-record reads +
   EnterRoom/LoadLevel/ExitRoom cold reads: one 14-19B identical block in
   bank0+bank2, `jsr` from ~10 overscan sites and the cold paths.
   **Band color = 1-byte ZP cache** set in EnterRoom (kernel-time bank switch
   is impossible — kernel code is in bank0).
3. **M3 (fold whole leaf) is the upgrade path** if fold-per-read shows up in
   timing: only if measurement demands it (HERO's preference — reader lives
   with the data).
4. **Mapper stays F6.** F6SC/E7 noted as RAM-rich alternatives if a future
   stage wants a shadow buffer; not needed for this design.
5. **Phased, each phase gated in Stella:**
   - **P0 — bootstrap space:** raise ~14B contiguous in bank0 (widen `$FEF7`
     hole by relocating one post-pad leaf, or drop `$FB72` dead data).
     Verify: build green, game unchanged.
   - **P1 — empty fold block + guard:** place `FoldIndirect` (harmless
     no-op call added to ONE cold site), extend `verify_build.py` to assert
     block byte-identical bank0↔bank2 (same guard pattern as `$FC68`).
     Verify: game unchanged, guard fires if block drifts.
   - **P2 — move per-level data to bank2 + route cold reads** (EnterRoom,
     LoadLevel, ExitRoom, band-color cache). Level data generated into
     `bank2.asm` instead of `kernel.asm`. Verify: full playthrough —
     rooms/enemies/connections/water.
   - **P3 — route per-frame enemy-record reads** through fold in overscan.
     Verify: all movers behave, no roll/flicker (measure overscan with
     TIM64T if any doubt).
   - **P4 — plan E4 (moth) + E5** unblocked: bank2 has ~4K, main headroom
     restored by data removal (~400-500B from `$F9xx-$FBxx`).

### 10. User decision: ALL level data → bank2 + bank3 (2026-09-27)

User wants generated level data **only in bank2 and bank3** (~8K usable after
stubs/vectors ≈ 90-100 rooms at today's ~80B/room). How HERO's method
extends to this (two data banks instead of one):

**Reserved bytes in the data banks (F6 constraints):**
- bank3 keeps power-up reset stub @ `$F000` + vectors `$FFFA-$FFFF` (~14B
  reserved — data must org around them).
- bank2 keeps its switch stub + valid vectors (same ~14B; vectors are read
  from whatever bank is mapped, so every bank keeps a valid copy).
- Both banks otherwise 100% data + fold blocks.

**HERO's rule generalized — two coexisting patterns:**

- **Pattern A (pure HERO — reader lives with its data):** the bulk reader is
  *duplicated into the data bank*; bank0 folds in, the whole loop runs
  native, folds out. One switch per loop instead of per byte.
  - `LoadPFBuffer` (36 reads/frame) → copy lives **beside the models it
    reads**; VBLANK cost ≈ today's loop + ~10c.
  - rect walkers → same bank as `MxRoomRects`.
  - Duplication cost: ~40-100B per reader **per bank** that holds its data —
    this is the "mini-code" (never the game).
- **Pattern B (fold fetch — generic cross-bank read):** one identical
  `FoldIndirect` block (§6) in bank0 + bank2 + bank3, `DataBankSel` picks
  the target (`$1FF8`/`$1FF9`). Used for the scattered reads: enemy records
  (16 sites), `EnterRoom`/`LoadLevel`/`ExitRoom` tables — ~10 per-frame
  folds in overscan ≈ 300c (budget 2240c) + cold paths.
- **Bank color stays a ZP cache** (kernel-time switch still impossible).

**Partition suggestion (minimizes Pattern A):**
| Bank | Contents | Readers folded in |
|------|----------|-------------------|
| bank0 | game code only (+ fold block, bootstrap 14B) | — |
| bank1 | HUD (unchanged) | — |
| bank2 | `models_data` + levels 0,1,... + fold block | `LoadPFBuffer`, rect-walk core (Pattern A), fold block (Pattern B) |
| bank3 | remaining levels + reset stub + vectors + fold block | enemy/level table readers only if Pattern B timing fails (else none) |

- Data addresses stay **byte-identical to today's layout offsets** where
  convenient, so ZP pointer values (`RoomPFxLo/Hi`, `RoomRectsLo/Hi`,
  `EnemyDataLo/Hi`) keep working unchanged — only the bank behind them
  changes.

**Cost of "all data out of bank0":** the models (`$F9xx-$FBxx` ≈ 600B) +
level tables leave main → bank0 main headroom jumps from 4B to ~600B
(E4/E5 code fits again), but the **14B fold-block bootstrap (P0) is still
required first** — callers live in bank0.

**Sequencing unchanged** (§8 P0→P4), with P2 now emitting generated data
into `bank2.asm`/`bank3.asm` instead of `kernel.asm`, and `LoadPFBuffer`
+ rect walkers gaining Pattern-A copies in bank2.
