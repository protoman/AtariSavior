# Generate Levels — campaign generator plan (editor menu)

Status: **plan / not implemented**. Written 2026-10-19.

Goal: one menu action in the PC editor — **Levels ▸ Generate 20 Levels…** — that
replaces `src/rooms/` + `src/rooms/models/models.json` with a complete, playable,
progressively harder 20-level campaign (models, levels, rooms, enemies, lamps,
water/raft, phase/vcrunch/hcrunch, doors+keys, branching paths), ending every
level on a catchable miner, fitting the ROM, with the generator validating and
play-testing its own output in the background.

---

## 0. Definition of done

1. `Levels ▸ Generate 20 Levels…` produces `level_001..020.json` +
   `models/models.json` with zero hand editing.
2. `./build.sh` green (all banks, both sims) and the whole test battery green
   after generation.
3. All 20 levels are reachable from the title (SELECT cycles 1..20) and each
   level's miner can be caught; level 20 wraps to level 1 as today.
4. Generated data fits the ROM with a measured per-bank slack printout
   (fail-fast, never a cryptic DASM `Origin Reverse-indexed`).
5. The previous stage is backed up before replacement; a failed generation
   leaves the working stage untouched.
6. The generator proves "playable" with the bounded self-test of §5 (structure
   + budget + build + scripted autoplay replay); anything it cannot prove is
   reported per level in the dialog log, never silently accepted.

## 1. What exists today (measured, 2026-10-19 build)

### 1.1 Data model

- `rooms/level_00N.json` = cereal `LevelData`: palette, `start_room`,
  `miner_room/x/y/dir`, `rooms[]`; each `RoomData` = `model_id`, grid
  `room_x/room_y`, `enemies[]`, `lamps[]`, `bottom_band` + color,
  `asym_patches[]`, `feature_cells[]`.
- `rooms/models/models.json` = global `ModelData[]`: **10 cols × 3 bands**
  (reflected → 40 display columns), `mid_band_type` (0 solid / 1 hot).
- Room grids are generated by `tools/convert_level.py` from model + room async;
  `rooms/*.txt` are convert's debug output, never authored.

### 1.2 ROM budget today (F6 16K)

Measured with `convert_level._gen_data_size` and the bank2 slot map:

| item | bytes |
|---|---|
| level index (`levels_index.asm`, 14 B/level) | 56 |
| 4 level table files (2+2+6+6 rooms) | 334 |
| shared models (12) | 166 |
| **used** | **556** |
| bank2 data capacity (`spill_F767` 256 + `spill_F901` 111 + `spill_window` 261 + `spill_F840` 28) | **656** |
| free | **100** |

Per-level cost model (exact, from `write_tables`/`emit_room_block`):

```
index       14 B/level today     (13 after the reshape, see §3.2)
per room     8 B   (RoomDataTable word 2 + connections 2 + RoomEnemies 4)
per entity   4 B   (enemy/lamp/raft/key record; type,x,y,dir)
async room  13 + 2R B (R = rect count, R<=5)  → own PF(9)+meta(2)+rect stream
            +5 B per phase cell, +5 B for a vcrunch box / hcrunch prefix
model       13 + 2R B (shared by every room pointing at it)
```

(Doors add no feature record — they are M1/meta strips, 2 B in the room block.)

A progressive 20-level campaign (§4.3) is ~137 rooms, ~160 entities, ~30 async
rooms, ~25 models ⇒ **≈3.1 KB** of level data. 16K has 100 B free. This is the
single hard blocker and §2 resolves it first.

### 1.3 Hard constraints the generator must respect (all enforced by
`convert_level.py` / `verify_build.py` — the generator mirrors them, it does not
invent new ones)

| Constraint | Limit | Source |
|---|---|---|
| rooms per level | ≤ 15 (connection nibble is 0..14; design target ≤ 12) | `nibble_room` |
| objects per room | ≤ 2 = enemies + lamps + (miner if here); slot 3 collides with `LaserState` | verify_build, `MAX_ENEMIES` |
| lamps | room id < 8 (dark mask covers 0-7); lamp counts as an object | verify_build |
| door rooms | exactly one door patch, ≤1 enemy, no key/lamp/miner, room row-1 band solid | `resolve_asym_patches` |
| asym patches | ≤2 total, one column-x per side, M1 wall-hide envelope | `resolve_asym_patches` |
| keys | ONE key per level (`KeyHeld` is one bit), must be reachable before the door | kernel |
| phase / vcrunch / hcrunch | row 1 only, one kind per room, mutually exclusive with door | `convert_room.lines` |
| vcrunch / hcrunch rooms | no enemies, no lamps, no miner (shutter owns the sprite slot) | verify_build, convert |
| hcrunch | contiguous prefix cols 0..n of row 1 (emit every cell) | convert_room |
| vcrunch | bbox of all V cells (emit contiguous cells) | convert_room |
| phase | one record per cell (emit the cells to blink) | convert_room |
| hot band (`mid_band_type=1`) | phase forbidden on it; vcrunch/hcrunch allowed | convert |
| raft entity (type 7) | `bottom_band` room, y on model row 2, spawn cell OPEN water | convert, verify_build |
| tentacle (type 3) | `bottom_band` room, y on model row 2 | convert |
| static RAFT tile (6) | model row 2 only, room must be water | verify_build |
| rects per room | ≤5 cached (`RcBase` clamps; >5 walkers miss walls) — design target ≤4 | `EnterRoomB2`, verify_build warn |
| exit geometry | horizontal exits = model row 1 at col 0/9; vertical exits = cols 8-9 top/bottom band | kernel room transitions |
| level index Y | `Level*stride` must stay ≤255 → 20 levels need stride ≤13 | `LoadLevel` |
| title level digit | `.DATitle` writes ONE digit (comment: `LEVEL_COUNT ≤ 9`) → needs BCD tens fix | kernel |
| HUD banner | LV + 2-digit level, already supports ≤99 | bank1 `SetupScorePointers` |

### 1.4 Existing generator stub (replace, do not extend)

`DataSerializer::GenerateAll20DefaultLevels` exists but is **dead/broken**:

- one model per room (model-data explosion),
- carves vertical exits with `2*20 + x` and `x = 8..11` while the model is
  10 wide → writes out of bounds / wraps into row 1; same bug in
  `MainWindow::CreateRoomInDirection` (`kVertExitB = 11` with width 10) — **fix
  this first**, it silently corrupts models whenever the editor adds a room,
- no features, no connectivity graph, no budget, no validation.

So: keep the function name/registration points as scaffolding, rewrite the
body into the module set of §4.1, and fix the two exit-carving bugs.

## 2. Capacity verdict and ROM decision

### 2.1 Verdict

20 levels of increasing complexity **do not fit F6 16K**. Even the irreducible
floor (20 × 1 room) costs 20×13 + 20×8 = 420 B of the 656 B capacity before any
model; the campaign above needs ≈3.1 KB. Shrinking rooms to fit would contradict
"increasingly complex, multiple paths".

### 2.2 Recommended: expand to F4 32K (8 × 4K banks) + 2 data banks

- `savior.bin` becomes 32768 B, cart type F4 (Stella infers it from size).
- Bank select hotspots `$1FF6..$1FFD` = banks 0..7. Banks 0-3 keep their exact
  meaning (`$1FF6..$1FF9`), so **existing code and byte-identical twins are
  untouched**.
- New banks 4-7: **data banks** (levels' tables + models) with a small code
  block: the `$F000` 5-byte boot stub + RESET vector (mandatory: F4 power-up is
  an undefined bank — same rule as today, `check_boot_banks` extends to 8).
- Budget: levels 1-10 → bank 4, 11-20 → bank 5 (≈1.7 KB data + ≈600 B reader
  code each ⇒ comfortable). Banks 6-7 reserved.
- Cost: build/verify/sim/test plumbing (§3.1) plus the banked-reader design
  (§3.3). This is the honest price of the feature.

### 2.3 Fallback (only if the user vetoes the mapper change)

Keep 16K, cap the campaign at **6 levels × ≤3 rooms** (~500 B including index
and models shared with the current 4), no doors/crunch (their async blocks are
the expensive part), and say so in the UI. This is a different product than what
was asked; listed here only so the decision is explicit.

## 3. Architecture changes (prerequisite phase, before the generator)

### 3.1 F4 plumbing (mechanical, one change, big blast radius)

| file | change |
|---|---|
| `src/build.sh` | assemble `bank4.asm`..`bank7.asm`, pad each to 4096, `cat bank0..bank7`, 32K output |
| `src/bank4.asm`..`bank7.asm` (new) | boot stub `lda #0 / sta $1FF6 / jmp $F005`, RESET vector, data-bank code block (§3.3), level data |
| `tools/verify_build.py` | expect 8 banks; `check_boot_banks` over 0..7; per-bank `.lst` pair for every twin/tramp check; per-bank data slot map for `--precheck` |
| `tools/convert_level.py` | `emit_spills` → N data banks, one include list per bank, greedy first-fit per bank against measured capacities, writing each level's `data_bank` byte into its index entry |
| `src/sim_*.py`, `src/tools/*`, `tools/test_*.py` | `BANKS` arrays of 8; `len(blob) == 32768`; any `16384` assert |
| `tools/freeze_test_banks.sh` | capture 8 bank images/lsts |
| `src/docs/bank_layout.md`, `AGENTS.md` | F4 map + reserved-read window |

**Reserved read window grows:** Stella's enhanced cart switches banks on *reads*
inside `$FFF6-$FFFD` (F6 today: `$FFF6-$FFF9`). Rule "no fetched byte at
`$xFFF6-$xFFF9`" becomes `$xFFF6-$xFFFD` in **every** bank; add it to
`verify_build` (assert those bytes are fill in all 8 banks).

### 3.2 Level index reshape (20 levels)

`LoadLevel` computes `Y = Level*14` in an 8-bit register → level 19 would read
`266 & $FF = 10`. Fixes (**13 B/level → 19×13 = 247 ≤ 255**):

- drop `START_X`/`START_Y` from the entry (always 32/24 today; becomes kernel
  constants `#32`/`#24`) — −2 B,
- add one `bank` byte per level → 13 B: `start_room, miner_room(±dir bit),
  miner_x, miner_y, wall_color, wall_color2, data_bank` + 3 word pointers
  (`RoomDataTable`, `RoomConnections`, `RoomEnemies`).

Bank assignment is owned by **convert** (single source of truth): its packer
places each level into a data bank and writes the `data_bank` byte into that
level's index entry (the generator's `StageBudget` mirrors the same first-fit
rule). The kernel reads the byte, sets `DataBank`, then enters that bank for
the room tables.

`kernel.asm` `LoadLevel` stride arithmetic `*14` → `*13`.

### 3.3 Data banks and banked reads

Concept: **the current level's bank is `DataBank`** (ZP byte, 0..3 → bank 4..7).
Everything that reads level data must read it from that bank. Two mechanisms:

1. **Per-bank readers (duplicated bytes at identical addresses, the existing
   twin pattern):** `EnterRoomB2`, `StageBandTab` and the fold body get a copy
   in each data bank. Bank0's `EnterRoom`/fold tramps become *bank-aware*: a
   small dispatch picks the `sta $1FFA/$1FFB/…` stub for the active bank, then
   `jmp $F010` (fetched from the destination bank, exactly like today's twin).
   Cost per data bank ≈550 B; bank0 needs ~16 B for the dispatch (fund by
   moving one leaf helper to bank1's free `$F042-$F53F`).
2. **`BankReadByte` twin (≈7 B per data bank):** `lda (FetchPtr),Y` +
   `sta $1FF6` + `rts`. The two bank2 routines that read enemy records directly
   (`MothRoutine`, `LaserHitTestBody`) call it through a tramp instead of
   `lda (FetchPtr),Y`, so **those routines never need duplicating**. Contract:
   bank0 caller → tramp → bank2 `sta $1FFx` → data-bank `BankReadByte` →
   `sta $1FF6 / rts` back into bank2.

Data layout inside a data bank: `$F000` stub, then code block, then the rooms'
model blocks + level tables, then that bank's share of levels. The `data_bank`
byte in the level's bank2 index entry is the single source of truth for which
bank a level lives in.

Enemy records for a level live in **its** data bank (they are per-level data),
so the records pointer in `RoomEnemies` stays an in-bank pointer.

### 3.4 Level-count plumbing (20)

- `LEVEL_COUNT = 20` in kernel + bank1 hand copies (generated value; tests
  `test_level_bank.py` keep the sync gate).
- `.DATitle` level digit → BCD tens+ones (2 bytes of kernel code, level 0-99).
- HUD banner already supports ≤99.
- Level wrap after the miner works unchanged.

## 4. Generator design

### 4.1 Module layout (editor, C++)

New files under `src/tools/editor/src/` (kept Qt-free where possible so the
CLI selftest can drive them):

| module | responsibility |
|---|---|
| `CampaignSpec.hpp` | the curriculum table (§4.3): per level rooms, mechanic budget, palette, twist flags |
| `RoomGraph.{hpp,cpp}` | build the room graph (grid coords, parent/child, branches, dead ends) |
| `RoomBuilder.{hpp,cpp}` | model shape per archetype + exit carving + feature cells + entities |
| `ModelLibrary.{hpp,cpp}` | intern/dedupe model blocks (hash tiles+`mid_band_type` → id), keep ≤~30 models |
| `LevelAssembler.{hpp,cpp}` | compose a `LevelData` from graph + rooms + miner + palette; emit intended route (§5.4) |
| `StageBudget.{hpp,cpp}` | byte accounting identical to convert's cost model; per-level and per-bank totals |
| `StageValidator.{hpp,cpp}` | mirror of convert/verify rules + structural reachability; no writes |
| `CampaignGenerator.{hpp,cpp}` | orchestration + progress callbacks + cancel token |
| `GenerateLevelsDialog.{hpp,cpp}` | Qt dialog, progress, log, cancel |

`DataSerializer` gains `SaveCampaign(dir, levels, models)` (writes through the
existing cereal serializers so formatting stays byte-consistent).

### 4.2 Determinism

`std::mt19937_64` seeded by the dialog's seed string (default `"1984"`).
Same seed + same curriculum ⇒ byte-identical JSON. Every random choice is
drawn from this engine only (no time, no hash-order dependence); the model
dedupe hash is content-based, not pointer-based.

### 4.3 Curriculum (20 levels)

Difficulty knobs: rooms, branches, entity budget, hot band, water %,
special-feature rooms, timer pressure (future), and mechanic introduction
order (one new mechanic per level, then mixes).

| L | rooms | introduce | shape / mix | palette |
|---|---|---|---|---|
| 1 | 3 | flight, landing, spider | linear vertical, empty caves | Red/Orange |
| 2 | 4 | snake patrol, bomb a fragile wall | one detour | Cyan/Blue |
| 3 | 4 | bat + moth, hot middle band (1 room) | vertical + side | Green |
| 4 | 5 | lamps (dark room, id<8) | one dark room with 2 enemies | Yellow/Gold |
| 5 | 5 | water + tentacle | ledges + water kill line | Purple |
| 6 | 6 | **ferry raft** (moving) | wide water crossing | Crimson |
| 7 | 6 | static raft platforms + bat over water | precision flight | Teal |
| 8 | 6 | phase wall (blinking) | timing gate | Ochre |
| 9 | 6 | vcrunch shutter (alone) | pass while open | Deep Blue |
| 10 | 7 | hcrunch prefix band | detour route | Pink/Rose |
| 11 | 7 | **door + key** (key in a side branch) | branch must be explored | Lime |
| 12 | 7 | dark room + door | lamp, then keyed door | Amber |
| 13 | 8 | two-path branch (short/risky vs long/safe) | both must reach | Sky Blue |
| 14 | 8 | raft + phase | water timing | Violet |
| 15 | 8 | vcrunch + hot band | hot shutter rooms | Olive |
| 16 | 9 | hcrunch + door + key | 3-stop route | Magenta |
| 17 | 9 | water gauntlet (tentacles + raft + ledges) | high entity count | Emerald |
| 18 | 9 | branching maze + key backtrack | dead ends | Purple Blue |
| 19 | 10 | everything, tight paths | mixed | Copper |
| 20 | 10 | finale: all mechanics, longest route | mixed, 2 crunch rooms | Silver |
| **Σ** | **137** | | | |

Rules encoded in `CampaignSpec` per level (not hardcoded in builders):
`rooms`, `newMechanic`, `hotRooms`, `waterRooms`, `specialRooms`, `door`,
`key`, `branches`, `deadEnds`, `entityBudget`.

### 4.4 Room graph

- Start room is `room_id 0` at grid `(0,0)` (level `start_room = 0`).
- Grow a spanning tree by random walk in grid coords (±1 in x or y, one room
  per cell), then add `branches` extra edges as shortcuts and `deadEnds` as
  optional rooms. Cap at 12 rooms and at grid cells with unique positions.
- Room ids assigned by BFS from start, so `room_id` order matches the intended
  route (helps the autoplay route and the 8-bit dark mask: keep lamp rooms in
  ids 0-7).
- Miner = deepest room of the *main* path (not a dead end), id < 15.

### 4.5 Rooms, models, exits

Exit carving (fixed geometry, correct widths — this replaces the buggy
`2*20+x` / `8..11` code):

- horizontal: model row 1 col 0 (left) / col 9 (right) → AIR; the transition
  row is the middle band only.
- vertical: top/bottom band cols 8-9 → AIR (cols 10-11 never touched; model is
  10 wide).
- Carve an exit only where the graph has an edge; the neighbour carves the
  matching one. Never carve an exit into a wall that must stay solid for a
  special room (door/crunch bands stay closed).

Archetypes (`RoomBuilder`) supply the mid-band shape, then exits are carved:

| archetype | shape |
|---|---|
| `Shaft` | open center shaft, side ledges |
| `Ledges` | alternating shelves (flight practice) |
| `WaterCrossing` | bottom band water + 2-3 ledges; ferry or raft tiles |
| `WaterGauntlet` | water + tentacle, one narrow ledge |
| `HotGallery` | `mid_band_type=1`, scattered safe pockets must be AIR cells |
| `PhaseGate` | row-1 wall with one contiguous open lane; phase cells flank it |
| `VCrunchPass` | open row-1 corridor; V cells in an inner bbox |
| `HCrunchBand` | row-1 prefix 0..n; detour through top or bottom band |
| `DoorRoom` | row-1 wall with one door column, solid everywhere else |
| `KeyRoom` | normal room plus a key entity |
| `DarkRoom` | normal room with a lamp, no other light source |
| `BranchHub` | 2-3 exits, small |
| `DeadEnd` | 1 exit, optional enemy |

Model dedupe key = `(tiles, mid_band_type)`, so 137 rooms collapse to ~20-30
models; the budget gate fails generation if the library exceeds the model budget.

### 4.6 Feature placement rules (generator-side, same as §1.3)

- One **new mechanic per level** first, mixes later (curriculum).
- Special rooms are alone (door XOR phase XOR vcrunch XOR hcrunch) and own a
  room async block.
- Vcrunch/hcrunch rooms get **no entities**.
- Door: exactly one patch `[1, col, 9, 0]` (right) or `[1, col, 9, 1]` (left);
  the door room's row 1 is otherwise solid; the key entity is placed in a room
  reachable *before* it (BFS order enforced).
- Phase: emit one feature cell per blinking cell, all in row 1, never on a hot
  model.
- Hcrunch: emit cells for cols `0..n` (prefix) and route the detour through the
  other band.
- Water rooms: `bottom_band = true` + a color; tentacle entities only on row 2;
  raft entity spawn cell must be open water; raft tile (6) only in row 2.
- Lamps: room id < 8, and the room must not be a door/crunch room.
- Objects per room ≤ 2 (miner counts); entity budget from the curriculum caps
  the total.

### 4.7 Miner

`miner_room` = deepest main-path room; `miner_x` in 0..19, `miner_y` in 0..11;
the cell under the miner must be solid and the cell above open (the generator
picks the geometry and asserts it); miner room gets no door/crunch and at most
one other object (2-object cap).

### 4.8 Byte budget

`StageBudget` computes the exact §1.2 cost model while building:

- per level: `13 + 8*rooms + 4*entities + Σ(async blocks)`;
- global: models + index (13 B/level);
- assign level → data bank greedily (levels 1-10 → bank 4, 11-20 → bank 5 by
  default, then let the packer move a level if a bank overflows);
- fail with `"bank 5: level 17 needs 96B, 38B left — reduce rooms or share
  models"` before writing anything. Target slack ≥100 B per bank.

## 5. Validation and self-test (the "it tests itself" part)

Ordered cheapest → most expensive; all run **before** the stage is replaced
(except the optional build, which runs against a staged copy).

### 5.1 Structural validator (in-process, ms)

- Graph reachability: every room reachable from `start_room`; every exit has a
  matching neighbour and an open edge corridor; no room at duplicate grid pos.
- Miner reachable; key reachable before the door (BFS order / `KeyHeld` rule);
  one key per door level, zero keys without a door.
- All §1.3 rules re-checked on the assembled structs (objects, lamps rooms,
  specials alone, water/raft/tentacle rows, rect count ≤5, hcrunch prefix).
- Physics sanity per edge: the exit corridor is open across the full sprite
  width (8 px) and the player can fly from the room's landing to it (generator
  records the waypoints; validator re-walks them against the generated solid
  map, 8 px steps, no wall overlap).
- Timer sanity: total path length ≤ fuel budget (`TickCounter`/`BarLevel`
  model in `sim_frame_budget`), with a safety factor.

### 5.2 Budget gate (in-process) — §4.8, hard-fail before write.

### 5.3 Real pipeline gate (subprocess, seconds)

Stage the generated files in a temp dir, then run the **real** tools against
that copy:

1. `tools/convert_level.py` per level + `--levels` (this is the authoritative
   rule checker — the generator must never duplicate a rule laxer than convert),
2. `tools/verify_build.py --precheck` with the temp stage (per-bank slot fit),
3. `./build.sh` against the staged stage (`FREEZE_STAGED`-style env already
   exists for the freeze script; reuse the mechanism), capturing output in the
   dialog log; `sim_bomb_fuse` + `sim_frame_budget` run as part of it.

### 5.4 Scripted autoplay replay (py65, ~1-2 s per level)

`tools/qa_campaign.py` (new): boots the built ROM (same boot sequence as
`qa_sweep.boot()`), selects the target level, then replays the route the
generator recorded: a list of `(room_id, waypoints, action)` steps, converted
to joystick/thrust frames. Assertions per level:

- every recorded room transition actually happened (RoomNo changes through the
  recorded sequence),
- the miner room is entered and the miner pickup fires (DropTarget = $FE tally
  starts / level advances),
- no unintended death (lives unchanged unless the route says so).

Boundary (be explicit): this proves the **intended** route works, not that every
route is fair — general solvability is out of scope. If the route replay is
flaky, the level is **reported**, not auto-shrunk; the fallback gate is
§5.1-5.3.

### 5.5 Failure policy

- Any §5.1-5.2 failure: nothing is written; the dialog shows the offending
  level/room and a "regenerate with another seed" hint.
- §5.3 build failure: stage restored from backup automatically; log kept.
- §5.4 replay failure: stage is still written (build is green) but the level is
  flagged "route unproven" in the log/manifest; the user can regenerate.

## 6. Editor UX

### 6.1 Menu and dialog

```
Levels ▸ Generate 20 Levels…      (new top-level menu)
       ▸ Verify Campaign…          (re-runs §5.1-5.3 on the current stage)
```

Dialog fields: `Seed` (text, default `1984`), `Levels` (spin, default 20),
`Rooms/level` curve (read-only preview from the curriculum), `Keep current
models` (off), `Run build + autoplay after generating` (on), `Backup current
stage` (on, forced), `Generate` / `Cancel`.

On accept: confirmation text states that `rooms/` and `rooms/models/models.json`
will be **replaced** (with backup) — this is the "erase all current ones" the
user asked for, made explicit and reversible.

### 6.2 Progress, cancellation, background

- `QProgressDialog` (0..100) with phase labels: `graph → rooms → features →
  entities → budget → validate → convert → build → autoplay`.
- Work runs on a worker thread (`QtConcurrent::run` + `QMetaObject::invokeMethod`
  for progress), so the UI stays responsive; cancel token checked between
  phases and between levels (cancelling never leaves a half-written stage).
- Subprocesses (`build.sh`, `qa_campaign.py`) run via `QProcess` with merged
  output appended to the dialog's log pane (last ~200 lines kept).
- Editor editing is disabled while running; the level list reloads on success.

### 6.3 Atomic write and backup

`<datadir>/rooms.generated/` (temp) → validated → then:

1. `rooms` → `rooms.bak-<UTC timestamp>/` (move, not copy; keeps the tree small),
2. `rooms.generated` → `rooms`,
3. models written inside the new stage before step 2; `src/generated/` is left
   to `build.sh` (never hand-edited).

Never write `src/tests/rooms` (tests own their stage — AGENTS rule).

### 6.4 CLI (headless, tests + CI)

```
savior_editor --generate-levels <datadir> [--seed 1984] [--levels 20]
               [--dry-run] [--verify] [--no-build]
```

`--dry-run` runs §5.1-5.2 and prints the budget table; `--verify` adds
§5.3-5.4. This is what the automated test executes.

## 8. Phases, gates and rough size

Each phase ends green (build + battery) before the next starts.

| phase | work | gate |
|---|---|---|
| **P0** | measure current budget (done — §1.2), fix the exit-carving width bugs (§1.4), decide mapper | plan approved |
| **P1** | F4 plumbing: build/verify/sims/tests 8 banks, boot stubs, reserved read window | 32K boots in sim + Stella, existing 4-level stage unchanged byte-for-byte (banks 0-3 identical) |

ROM cannot hold.

## 9. Risks and open questions

1. **Mapper change is user-visible** (ROM 16K → 32K). Everything else in this
   plan depends on it. → Decision needed before P1.
2. **Banked reads are the riskiest code** (twin/tramp discipline): every new
   reader must be byte-identical at the same address in each data bank, and the
   `$FFF6-$FFFD` read-trap window grows. Mitigation: `verify_build` twins
   checks extend per bank; py65 sims boot every bank.
3. **Autoplay replays only the intended route** — not a general solvability
   proof. Documented as a bounded guarantee (§5.4).
4. **Level dark mask covers rooms 0-7 only** — generator keeps lamp rooms in
   ids 0-7. Extending the mask is a kernel change, out of scope.
5. **Cursor/level-select UX for 20 levels**: SELECT cycles 1..20; the title
   digit fix (§3.4) is required, otherwise level 10+ shows "0".
6. **Combine with future content** (bosses, music) — not in this plan.
7. **User's current 4-level stage is erased** (backed up). If any of it should
   survive as a template, say so before P5; the generator can seed an archetype
   from it.
8. **Generator quality is subjective**: seed + curriculum give reproducible but
   "designed-by-rules" levels. Plan P5 includes a tuning pass with the user
   playing a few levels in Stella before the full battery is locked.
